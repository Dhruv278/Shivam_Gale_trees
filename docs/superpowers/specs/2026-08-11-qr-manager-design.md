# Image QR Manager — Design

**Date:** 2026-08-11
**Status:** Approved, in implementation

## Purpose

A one-time internal tool. A folder holds ~1,700 images. The operator opens a portal, clicks one
button to generate a QR code for every image, then downloads all QR codes as a single folder
(ZIP). Each QR PNG is named after its source image. Scanning a QR opens that image in a phone
browser — the image alone, nothing else.

## Scope

This supersedes `PDF-Image QR Manager - Final Project Plan.md`, which described a substantially
larger system. Deliberately **out of scope**: GitHub API uploads, Personal Access Tokens,
runtime `data.json` generation, Settings page, duplicate Skip/Replace/Rename handling, upload
progress against a remote host, PDF support, bulk delete/rename, categories, tags.

PDFs are out of scope because the operator has none. `SUPPORTED_EXTENSIONS` in
`src/lib/naming.mjs` is the single extension point if that changes.

## Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Framework | Next.js 16.3.0, React 19, JavaScript, Tailwind v4 | Operator's explicit request |
| Hosting | Vercel | GitHub Pages cannot serve dynamic routes; see below |
| Viewer URL | `/view/<slug>` path segment | Clean printable URLs |
| Image storage | Full-quality originals committed to `public/images/` | No quality loss; clears every documented limit — see Image storage |
| Deploy method | **Vercel Git integration only, never `vercel deploy` CLI** | The CLI path caps static uploads at 100 MB on Hobby |
| QR generation | Client-side, in-browser | No serverless timeout risk on a 1,700-item run |
| QR settings | 512×512 PNG, error correction M, 2-module quiet zone | Standard print tradeoff |
| Image delivery | Plain `<img>`, not `next/image` | Vercel optimization quotas would break scanned codes |

### Why not GitHub Pages

The original plan required GitHub Pages as the only host. A Next.js static export cannot
prerender `/view/:id` for IDs unknown at build time. Moving to Vercel resolves this and buys
clean path URLs. Note that once images are committed at build time, all slugs *are* known at
build time, so GitHub Pages would become viable again — Vercel was chosen anyway for simplicity.

## Architecture

```
public/images/            operator drops files here, commits, pushes
       │
  [prebuild hook]         scripts/build-manifest.mjs
       │
       ▼
src/data/manifest.json    [{ file, slug, qrName, name }, …]
       │
       ├──► /              Portal: list, search, Generate, Download ZIP   (client)
       └──► /view/[slug]    Bare image viewer, prerendered                (server)
```

No backend, no database, no tokens. The manifest is generated by npm `predev`/`prebuild` hooks so
dev and production always agree and nothing reads the filesystem at request time — Vercel's
runtime filesystem is read-only.

At ~1,700 entries the manifest is roughly 100 KB of JSON, shipped to the client, which needs the
full list anyway to generate QR codes.

## Naming

Two names are derived per image and must never be conflated:

| | Purpose | `Front Label.jpg` → |
|---|---|---|
| `slug` | URL segment encoded in the QR | `front-label` |
| `qrName` | Filename inside the ZIP | `Front Label.png` |

`qrName` preserves the original basename verbatim — that is the operator's stated requirement.
`slug` is lowercased, accent-stripped, and hyphenated so URLs stay clean and ASCII.

**Collision handling.** Files are sorted before processing so suffixes are deterministic across
builds; otherwise filesystem ordering could reshuffle which image owns `front-label` between
deploys and invalidate already-printed codes.

- `Front.jpg` + `Front.png` both want `Front.png` → second becomes `Front-2.png`
- `A B.jpg` + `a-b.jpg` both slug to `a-b` → second becomes `a-b-2`

QR filename deduplication is **case-insensitive**, because extracting a ZIP on Windows or macOS
collapses case and would silently drop a QR code from the print run.

Every collision is reported as a build warning rather than silently applied.

## Portal (`/`)

- Base URL banner at top, from `NEXT_PUBLIC_SITE_URL` falling back to `window.location.origin`,
  showing a full example QR target. An amber warning appears when the env var is unset, because
  printing 1,700 codes against the wrong domain is the expensive failure mode.
- Image count, realtime search on name/file.
- Row list capped in the DOM (windowing or pagination) with lazy thumbnails — 1,700 one-megabyte
  thumbnails at once would jank the page and waste bandwidth.
- Per row: thumbnail, filename, slug, viewer URL, Copy URL, Open, Download single QR.
- `Generate QR Codes` → live `n / total` progress with a bar. The loop yields to the event loop
  periodically so progress actually paints.
- Generation is fault-tolerant: a per-image failure is collected and reported at the end; the
  remaining codes still download.
- `Download QR Codes` appears only after generation, bundling every PNG into `qr-codes.zip`.
- Empty state explains that files go in `public/images/` and `npm run manifest` refreshes the list.

## Viewer (`/view/[slug]`)

Server component, prerendered for all slugs via `generateStaticParams`, so scans hit CDN-cached
HTML. Renders exactly one thing: the image, centered, `object-contain`, on a neutral dark
background, fitting any phone screen without horizontal scrolling. No header, filename, download
button, or navigation.

`params` is a Promise in Next.js 16 and must be awaited. Filenames contain spaces, so the image
URL segment must be encoded or it 404s. Unknown slug renders a minimal "Image not found" line —
rendering literally nothing would look like a broken site.

## Error handling

| Condition | Behaviour |
|---|---|
| `public/images/` missing | Empty manifest written with a warning, portal shows empty state |
| Unsupported file in folder | Skipped, counted in build output |
| Slug or QR name collision | Deterministic suffix, build warning |
| `NEXT_PUBLIC_SITE_URL` unset | Prominent warning; generation still allowed for local testing |
| Single QR generation failure | Collected, reported, other codes still downloadable |
| Unknown slug scanned | Minimal "Image not found" |

## Testing

Vitest, node environment, `src/**/*.test.mjs`.

- `naming.test.mjs` — slug derivation, `qrName` derivation, collision resolution, determinism,
  digit preservation, case-insensitive dedupe. 19 tests.
- `qr-roundtrip.test.mjs` — generates a QR at production settings, decodes it with `jsqr`, and
  asserts the decoded string is exactly the expected viewer URL. This is the highest-value test in
  the project: it proves the printed artifact is correct, not merely that the code ran.

## Image storage: resolved

The design was originally sized against an estimate of 2–3 KB per image. The real images are
**2675×4754 print-resolution JPEGs averaging 1,041 KB** — about **1.77 GB** across 1,700 files.

**Decision: commit the full-quality originals and deploy via the Vercel Git integration.**
No resizing, no re-encoding.

### Why not downscale

The images are GAIL tree-information posters carrying a data table and fine print (species,
lifespan, CO₂ absorption, medicinal notes). Viewers pinch-zoom to read that text, so resolution is
functional, not decorative. A 1200px copy looks fine until zoomed, then goes soft.

Re-encoding to WebP was considered and rejected: lossy WebP is a *second* lossy pass over an
already-lossy JPEG, and lossless WebP on JPEG-sourced photos generally produces **larger** files.
Lossless JPEG re-optimisation saves only 5–15%, which does not change the problem.

### Verified limits (checked 2026-08-11)

| Limit | Vercel Hobby | 1.77 GB verdict |
|---|---|---|
| Static file uploads — **CLI deploys only** | 100 MB | ❌ would fail |
| Build container disk | 32 GB | ✅ clears easily |
| Build memory | 8 GB | ✅ |
| Build duration | 45 min | ✅ |
| Source files per deployment | 15,000 | ✅ 1,700 |
| Fast Data Transfer | 100 GB/month | ✅ ~100,000 scans/month |

**The 100 MB cap is scoped to `vercel deploy` from a workstation.** Git-integration deploys clone
into a 32 GB build container instead, so the cap does not apply.

> **Do not deploy with the Vercel CLI.** That path fails at 100 MB on Hobby. Push to GitHub and let
> the Git integration build.

### Accepted trade-offs

- The repo reaches ~1.8 GB, above GitHub's recommended 1 GB (5 GB is the strong ceiling). It works;
  pushes, clones, and Vercel's per-build clone all get slower.
- Vercel does not *explicitly* document a static-asset ceiling for Git deploys, so a small residual
  unknown remains.

### Fallback

If a build ever fails on size, move the images to **Cloudflare R2** (10 GB free storage, free
egress) and repoint the image base URL. The viewer constructs that URL in one place, so this is a
configuration change rather than a rewrite.
